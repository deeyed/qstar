# QStar v0.8.0 Beta Release Candidate Gate

This is the release-candidate checklist and draft release note for the future
QStar `v0.8.0-beta` feature line. It is not a published release note yet. Q251
turns the scattered 0.8 release checklist into one local Makefile gate plus one
documented hosted validation plan.

Runtime version target:

```txt
qstar 0.8.0-beta
```

Until the version bump/tag round lands, the current checkout may still print the
previous public beta version. `make qstar-v0.8-release-tests` validates the
0.8 gate shape against the current runtime; the final release run must happen
from a clean checkout whose `QSTAR_VERSION` and release tag agree.

## Release Decision

`0.8.0-beta` should focus on Windows beta readiness, Windows shared library
implementation, and the release gates needed to keep that support honest.
`0.7.x-beta` remains the patch-only line for release/package smoke,
documentation drift, and CI artifact fixes.

## Local Release Candidate Gate

Before tagging a future `v0.8.0-beta`, run the umbrella gate:

```sh
make qstar-v0.8-release-tests
```

The target expands to:

- `make check`
- generic DSL backend parity
- optional real GLP compiler corpus
- real-language `qstar init` scaffold validation
- repeat medium/large performance release summaries
- current-host public beta package smoke
- Windows release package and extracted-asset contract smoke
- `git diff --check`
- `build/bin/qstar --version`

The GitHub release download smoke needs already-published assets, so it is
opt-in instead of part of the default local gate:

```sh
QSTAR_RUN_RELEASE_DOWNLOAD_SMOKE=1 make qstar-v0.8-release-tests
```

When the variable is not set, the target prints:

```txt
qstar-v0.8-release-tests: download-smoke=skipped reason=requires-published-release-asset
```

## Candidate Highlights

- Windows validation-backed beta candidate lane.
- Windows process/event runner boundary for non-POSIX hosts.
- Windows `.exe` and explicit static `.lib` validation on real Windows hosts.
- Windows `qstar.sharedlib` runtime `.dll` plus import `.lib` artifacts.
- Stella/Ninja parity for Windows artifact maps and sharedlib lowering.
- Windows `windows-x86_64` zip asset candidate generated and extracted in the
  manual beta candidate workflow.
- Daemon lifecycle/security hardening while keeping daemon opt-in.
- macOS arm64 and Linux x86_64 hosted asset smoke freshness.
- Performance gate summaries using the Q176 release artifact table format.

## Asset Plan

```txt
qstar-v0.8.0-beta-macos-arm64.tar.gz
qstar-v0.8.0-beta-linux-x86_64.tar.gz
qstar-v0.8.0-beta-windows-x86_64.zip
SHA256SUMS
```

macOS arm64 is the current local packaging host. `make qstar-public-beta-package`
produces the current-host tarball and checks installed docs, manpages, provider
bundles, checksums, and extraction smoke.

Linux x86_64 must be produced by Ubuntu CI or a clean Linux x86_64 host.
The Linux workflow dry-run package gate proves the layout, and release
publication remains an explicit `workflow_dispatch` upload step.

Windows asset publication is not automatic for 0.8. The manual Windows workflow
can produce a zip candidate and run extracted package smoke. A Windows asset can
be added to GitHub Releases only if native build, install smoke, artifact policy,
package smoke, and uploaded/downloaded asset smoke pass on a Windows host.

## Gate Checklist

Local gate:

```sh
make qstar-v0.8-release-tests
```

Published asset download smoke, after GitHub Release upload:

```sh
QSTAR_RUN_RELEASE_DOWNLOAD_SMOKE=1 make qstar-v0.8-release-tests
```

Linux hosted fresh run:

```sh
gh workflow run linux-validation.yml \
  --ref main \
  -f release_tag=v0.8.0-beta \
  -f publish_linux_asset=false \
  -f daemon_socket_smoke=true
```

Only set `publish_linux_asset=true` after the release tag exists and the release
asset upload is intentionally in scope.

Windows candidate fresh run:

```sh
gh workflow run windows-validation.yml \
  --ref main \
  -f run_ninja_parity=true
```

The Windows workflow uploads `qstar-windows-beta-candidate` with
`windows-beta-candidate-status.txt`, `KNOWN_ISSUES.md`, and failure detail dirs,
plus `qstar-windows-beta-release-asset` with the generated zip candidate,
`SHA256SUMS`, package reports, and extracted package smoke logs.
The named sharedlib parity gate covers `.dll`, import `.lib`, executable
consumer link, install/stage layout, and unsupported PDB/debug behavior.

## Explicitly Deferred

- Daemon default-on behavior.
- Stable daemon protocol promise.
- Windows named pipe daemon, unless a later 0.8 readiness update explicitly
  takes ownership of it.
- Remote daemon access.
- Package resolver, registry, lockfile, and fetch policy.
- External language Ninja wrapper lowering beyond the sealed provider/backend
  contracts.
- VSCode Marketplace publication.

## Notes

- Makefile remains QStar's canonical bootstrap and release build path.
- QStar self-host remains a release gate candidate and backend parity check.
- Linux assets must be produced by Ubuntu CI or a clean Linux x86_64 host.
- Windows artifacts require real native validation before publication.
- QStar is licensed under Apache-2.0. Lua vendor license text is preserved in
  `LICENSE/lua.txt`.
